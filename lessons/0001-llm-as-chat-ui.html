Make an LLM useful in chat

The key idea: the LLM writes and plans; your application supplies truth, permissions, and actions.

The loop

When a Cloud Compass user asks, “Why did our AWS spend rise?”, the browser sends the message to a backend. The backend authenticates the user, resolves their tenant, retrieves relevant cost data, and gives the model a structured description of the available read-only tools. The model may request cost.get_costs. Your server executes that request, checks authorization again, and returns the result to the model. The model then writes an explanation with citations. The backend streams that answer to the browser.

Never ask the model to be the database, the authorization layer, or the cloud SDK. It is the language-and-planning layer.

What the UI should show

Show the user’s message, a streamed assistant response, and—when relevant—a compact “Checked AWS cost data” activity row with the time range and source. Keep tool arguments and raw secrets out of the UI. Render citations as links or evidence cards, not as implied certainty.

Practice: classify the parts

For each item, decide whether it belongs to the model, the application, or the cloud tool:

  1. Choose whether a cost query is needed.
  2. Verify that the user belongs to tenant A.
  3. Return daily AWS spend for March.
  4. Explain the increase in plain language.
Check your answer

1 model · 2 application · 3 cloud tool · 4 model (using evidence supplied by the application).

One design rule

Separate conversation from truth. Conversation history helps continuity; fresh tool results and retrieved runbooks support factual claims. If no evidence is available, the assistant should say so.
